\chapter{Results}
\label{chap:results}

In evaluating the performance, it is important to note that the datasets used were
specifically developed and reverse-engineered for this study to simulate real-world cases.
A key uncertainty remains whether these synthetic datasets are sufficiently complex or
large enough to reach the ``tipping point'' where the custom architecture's
strengths truly manifest. Therefore, the evaluation should prioritize the performance
trends across sessions as a case progresses, rather than focusing solely on
aggregate performance metrics.

The fundamental trade-off addressed in this research is cost versus accuracy.
While baseline models—which ingest the full context for every query—may offer
higher granular precision in smaller datasets, this ``stateless agent'' approach
is not scalable. In larger, multi-year cases, passing the entire history
becomes prohibitively expensive and computationally slow. The custom architecture
accepts a marginal risk in retrieval error to achieve sustainable
operational costs and long-term scalability.

A human analogy is helpful to illustrate the architectural philosophy:
A legal professional working on a massive case does not re-read every
single document in the archive before answering a new question.
Instead, they rely on a structured ``factsheet'' or summary (the case state)
and perform targeted lookups when specific details are required.
While reading every page every time might provide the most detail,
it eventually leads to cognitive overload where one ``mixes up the cards.''
By utilizing a condensed case state, the custom architecture avoids
this ``context confusion'' while maintaining a manageable overhead.

Consequently, for the smaller datasets created for these tests, the baseline
models often perform better because the room for retrieval error is eliminated
when everything fits in the prompt. However, as the volume of information
reaches realistic proportions, the necessity of the ``factsheet'' approach
becomes clear. The extraction process not only manages costs but also
yields a structured, machine-readable state that can be seamlessly
integrated into front-end systems for human oversight, bridging the
gap between raw data and actionable legal insights.

\section{Expected Performance Patterns}
% -------------------------------------------------------

Before presenting the empirical results, this section outlines the a priori expectations
that motivate the experimental design. These expectations are grounded in the architectural
differences between the two agent configurations and in the nature of legal case progression.

\paragraph{Quality metrics over session progression.}
The central hypothesis is that the performance trajectories of the two architectures diverge
as a case progresses. In the earliest sessions, the document set is small and the total
context volume is modest. Under these conditions the baseline agent—which passes all
available documents directly into the prompt—benefits from complete information exposure
and is expected to perform comparably to, or even above, the custom agent. The custom agent
at this stage relies on a factsheet that has only been populated from a limited number of
documents, meaning its structured state may not yet be rich enough to fully substitute
for direct document access.

As subsequent sessions introduce new documents, new parties, additional claims, and a
growing timeline, the situation reverses. The baseline agent's context window fills with
an ever-larger payload, increasing the risk of retrieval confusion, cross-document
interference, and eventual context overflow. The custom agent, by contrast, maintains a
continuously updated factsheet and performs targeted retrieval against an expanding vector
index, allowing it to leverage accumulated case knowledge rather than being overwhelmed
by it. The expected result is a positive trajectory for the custom agent across sessions
and a flat or degrading trajectory for the baseline.

\paragraph{Token usage over session progression.}
Token usage is expected to grow for both architectures as the case accumulates material,
but for structurally different reasons. For the baseline agent, input token growth is
largely forced: more documents means a larger prompt, and the agent has no mechanism to
suppress irrelevant context. For the custom agent, input token growth reflects increasing
\emph{richness} rather than raw volume: the factsheet grows denser, the vector index
returns more contextually relevant chunks, and the agent incorporates more detail into its
reasoning. Output tokens are likewise expected to grow over time for the custom agent, as
richer context enables more thorough and nuanced answers. This growth is therefore a
positive signal—evidence that the agent is leveraging accumulated case knowledge—rather
than an efficiency cost.

\paragraph{Inference time.}
Response latency is expected to remain relatively stable for the custom agent, since
retrieval is bounded by configurable top-$k$ limits and the factsheet is loaded once per
query rather than reprocessed. The baseline agent's latency is expected to increase with
document volume, as larger prompts impose greater prefill costs on the LLM and increase
the risk of multi-step tool calls to handle context that cannot fit in a single pass.

\section{Case: THRD-2021-163881}
% -------------------------------------------------------

The following results are reported for case THRD-2021-163881. This case was selected as
the primary reporting case because it contains the largest document volume among the three
evaluation datasets, making it the most demanding test of the scalability hypotheses
described above. The case spans four evaluation sessions, each introducing additional
documents and queries as the litigation progresses.

% -------------------------------------------------------
\subsection{Quality Metrics}
% -------------------------------------------------------

\subsubsection*{Correctness over Session Progression}

Figure~\ref{fig:lineplot-correctness} shows mean correctness per session for each agent
configuration. In session~0, the custom agent leads with a correctness of 0.91 compared
to 0.81 for the baseline. Both architectures dip in session~1—the first session that
introduces a substantial new document batch—with the custom agent falling to 0.73 and the
baseline to 0.70. This temporary convergence is consistent with the expected ``adjustment
period'' during which the factsheet is being updated to reflect new material but has not
yet been queried against the expanded index.

From session~2 onwards the trajectories diverge in the expected direction. The custom
agent recovers to approximately 0.82 and holds this level through session~3, while the
baseline continues to decline, ending at 0.63 in the final session. The gap between the
two architectures widens monotonically after the initial dip, from roughly 2 percentage
points in session~1 to approximately 19 percentage points by session~3. This pattern is
consistent with the hypothesis that the custom architecture's structured state management
becomes increasingly advantageous as case volume grows, while the baseline agent degrades
under the accumulating context burden.

    \caption{Mean correctness per session for the custom and baseline+RAG agents on case THRD-2021-163881.
             The custom agent recovers after an initial dip and stabilises above 0.82, while the

\subsubsection*{DeepEval Quality Metrics (Aggregate)}

Figure~\ref{fig:pairplot-deepeval} shows the joint distribution of correctness, relevancy,
and completeness across all queries and sessions, aggregated for each agent type.

The custom agent's correctness distribution (orange) is clearly right-skewed, with density
concentrated near 1.0, whereas the baseline distribution (blue) is considerably more
spread and contains a non-trivial mass at scores below 0.5. This confirms that the
correctness advantage observed in the longitudinal plot is not driven by a small number
of high-scoring queries but reflects a broad shift in the distribution.

Relevancy scores are highly concentrated near 1.0 for both configurations, indicating
that both agents are generally capable of producing on-topic responses. This suggests that
the divergence in correctness is attributable to factual accuracy rather than
off-topic generation.

Completeness shows a similar pattern to correctness: the custom agent's distribution skews
higher, while the baseline exhibits more low-completeness responses. This is consistent
with the expectation that the factsheet provides richer context for constructing
comprehensive answers, especially as the case grows in scope.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/pairplot_deep_eval_THRD-2021-163881.png}
    \caption{Pairplot of DeepEval quality metrics (correctness, relevancy, completeness) for
             case THRD-2021-163881. Diagonal panels show per-metric density estimates.
             The custom agent (orange) exhibits higher correctness and completeness, while
             relevancy is similarly high for both configurations.}
    \label{fig:pairplot-deepeval}
\end{figure}

\subsubsection*{BERTScore}

Figure~\ref{fig:pairplot-bert} shows the joint distribution of BERTScore components
(precision, recall, F1, and sentence-BERT similarity). Unlike the DeepEval metrics, the
BERTScore distributions for the two agents overlap substantially across all sub-metrics.
Both configurations cluster in a narrow high-scoring band: bert\_f1 concentrates around
0.65--0.70 and sentence-BERT similarity around 0.85--0.95 for both agents. The custom
agent's distribution is marginally shifted toward higher values in most panels, but the
difference is small relative to the spread of the data.

This result is not unexpected. BERTScore measures surface-level semantic similarity to the
reference answer and is therefore less sensitive to structured factual completeness than
the DeepEval metrics. A response can score well on BERTScore while omitting specific facts
that correctness and completeness evaluation would penalise. The near-identical BERTScore
distributions therefore complement rather than contradict the DeepEval findings: both
agents produce semantically coherent output, but the custom agent more reliably includes
the specific factual content required by the gold-standard reference.

\begin{figure}[h]
    \centering
    \includegraphics[width=\textwidth]{figures/pairplot_bert_THRD-2021-163881.png}
    \caption{Pairplot of BERTScore sub-metrics (precision, recall, F1, and sentence-BERT
             similarity) for case THRD-2021-163881. Distributions for the two agent
             configurations largely overlap, indicating comparable surface-level semantic
             quality while the DeepEval metrics reveal greater divergence in factual
             completeness.}
    \label{fig:pairplot-bert}
\end{figure}

\subsection{Resource Metrics}
% -------------------------------------------------------

Figure~\ref{fig:pairplot-resource} shows the joint distribution of resource consumption
metrics: inference duration, input tokens, output tokens, total tokens, and number of LLM
calls per query.

The most notable pattern is in input token usage. The custom agent (orange) spans a wider
range, with some queries consuming upwards of 200{,}000 input tokens. This is consistent
with the expectation that the factsheet—injected in full on each call—grows denser as the
case accumulates material, and that the vector retrieval step returns richer and more
numerous chunks. The baseline agent (blue) clusters at lower input token counts, reflecting
its simpler retrieval strategy, though it too exhibits high-token outliers corresponding to
sessions with large document sets.

Output tokens are similarly distributed, with the custom agent showing a slightly wider
tail toward higher values. This is in line with the expectation that a richer context
enables more detailed answers.

Inference duration is generally lower and more tightly concentrated for the custom agent,
with the baseline exhibiting heavier tails at high latency. The structured retrieval
mechanism of the custom agent—bounded by configurable top-$k$ limits—appears to reduce
the variance in response time compared to the baseline's unbounded document ingestion.

LLM call counts are comparable between the two configurations, typically in the range of
1--3 calls per query, indicating that neither architecture requires substantially more
agentic steps than the other to produce a response.
