\section{System Architecture}

The system is designed as a modular, client-server application consisting of four main packages organized as a \texttt{uv} workspace: \texttt{agent}, \texttt{ui}, \texttt{evals}, and \texttt{data-viewer}. The architecture follows a separation of concerns, where the backend handles all agent logic, data persistence, and document processing, while the frontend is responsible for user interaction and result presentation.

\subsection{Overview}

The backend is implemented as a \textbf{FastAPI} application (\texttt{agent/main.py}) that exposes a RESTful API with Server-Sent Events (SSE) for real-time response streaming. The frontend is a \textbf{Streamlit} application that communicates with the backend over HTTP, consuming streamed responses. Authentication is handled via \textbf{Supabase Auth} using JWT tokens, which are validated on each request through a \texttt{HTTPBearer} dependency in FastAPI.

\subsection{Agent Layer}

The core agent is implemented using \textbf{LangGraph's} \texttt{StateGraph}, a directed graph framework for building stateful LLM applications. The agent graph consists of two nodes:

\begin{itemize}
    \item \texttt{call\_llm} — Constructs the full input payload, including the system prompt, factsheet context, conversation history, and RAG-retrieved document chunks, then invokes the LLM.
    \item \texttt{call\_tool} — Executes any tool calls returned by the LLM.
\end{itemize}

A conditional edge routes control back to \texttt{call\_tool} if the LLM emits tool calls, or terminates the graph otherwise. To manage long conversations within the model's context window, a rolling summarization strategy is applied every eight messages using a dedicated \texttt{Summarizer} module.

Conversation state is persisted using LangGraph's \texttt{AsyncPostgresSaver} checkpointer, backed by \textbf{Supabase PostgreSQL}, enabling session resumption and multi-turn dialogue across requests.

\subsection{Tool Layer}

The agent has access to a set of callable tools defined in \texttt{tools.py}. The full tool set (\texttt{TOOLS}) used in the primary agent configuration includes:

\begin{itemize}
    \item \texttt{tavily\_search} — Web search via the Tavily API.
    \item \texttt{read\_attachment} — Fetches and parses a document from Supabase Storage.
    \item \texttt{query\_project\_attachments} — Performs semantic retrieval (RAG) against project-specific documents indexed in BigQuery Vector Store.
    \item \texttt{read\_laws} — Semantic retrieval against a corpus of Norwegian legislation.
    \item \texttt{update\_project}, \texttt{clean\_element}, \texttt{create\_project} — Tools for managing the factsheet state.
\end{itemize}

Two ablated tool configurations are also defined for evaluation purposes: \texttt{BASELINE\_TOOLS} (web search and law retrieval only) and \texttt{BASELINE\_RAG\_TOOLS} (web search, law retrieval, and project document RAG, but without file storage access).

\subsection{Data and Storage Layer}

Document persistence is handled through two complementary mechanisms. Raw files (PDF, DOCX, PPTX, EML) are stored in \textbf{Supabase Storage}, where they can be retrieved on demand by the \texttt{read\_attachment} tool. Parsed and chunked document content is embedded using \textbf{Google's \texttt{gemini-embedding-001} model} and stored in \textbf{BigQuery Vector Store} for semantic retrieval. Structured project data — including the \texttt{FactSheet} and session metadata — is stored in Supabase PostgreSQL via the \texttt{SupabaseManager} CRUD interface.

\subsection{Document Processing Pipeline}

Upon project initialization (\texttt{POST /init-project}), a multi-phase asynchronous pipeline is triggered:

\begin{enumerate}
    \item \textbf{Phase 1:} Documents are parsed using \texttt{DocumentProcessor} (supporting PDF with OCR, DOCX, PPTX, and EML formats), stored in file storage, and indexed in the vector store.
    \item \textbf{Phase 2:} Documents and emails are analyzed in parallel to extract structured entities — events, claims, damages, deadlines, and attachment metadata.
    \item \textbf{Phase 3:} Factual facts and governing law are synthesized across all documents.
\end{enumerate}

Status events are streamed back to the frontend via SSE throughout all phases.

\subsection{LLM Configuration}

The system supports multiple LLM providers through LangChain's \texttt{init\_chat\_model} interface. \textbf{Google Gemini} serves as the primary provider, with \textbf{OpenAI GPT} available as a secondary option. The active model is configurable per session request, allowing for flexible experimentation and evaluation across providers.

\section{Design Choices}

The system architecture was guided by several pragmatic design choices, prioritizing development speed, flexibility, and cost-efficiency given the constraints of a master's thesis. By separating the descriptive architecture from the rationale, the core motivations for the selected technologies are outlined below.

\subsection*{Agent Layer and Orchestration}

The core agent is implemented using \textbf{LangGraph} \cite{langgraph}. This framework was chosen primarily for its fast build time, which is essential given the limited time available for this thesis. It provides a clean \texttt{StateGraph} abstraction that is highly expandable for future extensions, such as adding dedicated reasoning nodes or document re-ranking stages. Furthermore, LangGraph is model-agnostic, providing built-in support for multiple LLM providers. This flexibility is crucial, allowing the system to easily switch between models or add new ones as desired for evaluation and experimentation.

\subsection*{Database and Storage Architecture}

The system's persistence layer separates structured relational data, unstructured document storage, and semantic vector retrieval to optimize for specific access patterns and constraints.

\paragraph{Relational Storage (PostgreSQL via Supabase):}
PostgreSQL was selected for its flexibility and highly efficient reads across tables. The structured nature of the factsheet state requires strict enforcement of relationships through primary and foreign keys to maintain data integrity and orderly matching on IDs \cite{supabase}. 
An initial attempt was made using a NoSQL database (Firestore); while easy and fast to set up, the lack of an enforced schema led to a loss of overview, with state inconsistencies and errors accumulating over time. Additionally, performing complex reads and combining data across different entities proved expensive and inefficient in NoSQL. 

Supabase was chosen as the PostgreSQL provider because it is affordable, open-source, and seamlessly integrates other necessary products like Authentication. Having these features included out-of-the-box makes the development process straightforward and fast.

\paragraph{File Storage (Supabase Storage):}
Raw documents (PDF, DOCX, EML, etc.) are stored in Supabase Storage. There were no specific architectural requirements for this other than cost-efficiency. 
Since Supabase was already selected for the PostgreSQL database, using its built-in, affordable object storage was a natural and convenient choice \cite{supabase}.

\paragraph{Vector Store and Embeddings:}
Semantic retrieval relies on \textbf{Google's embedding model} (\texttt{gemini-embedding-001}). This model was specifically chosen for its strong multilingual capabilities; smaller and cheaper open-source models often struggle with RAG matching when queries or documents are not strictly in English, which is a critical requirement for handling Norwegian legal texts.

For the vector database, a two-tier approach is used. \textbf{ChromaDB} is utilized as an in-memory store for fast, session-scoped retrieval. For persistent, project-scoped retrieval, \textbf{BigQuery Vector Search} is employed. BigQuery was chosen because it is affordable and operates on an on-demand pricing model. The primary drawback of BigQuery is its high latency, meaning a significant amount of time is spent indexing and saving to the vector store. However, this trade-off is worthwhile: the alternative would require provisioning an always-running vector database server, which introduces high continuous costs and additional operational setup.

\subsection*{FastAPI and Server-Sent Events}

The backend is exposed as a standalone REST API using \textbf{FastAPI} \cite{fastapi} to decouple it from the frontend. \textbf{Server-Sent Events (SSE)} are used for streaming responses because the agent pipeline is long-running and asynchronous. SSE provides a responsive user experience by pushing incremental status updates and partial results without the complexity of WebSockets, which are unnecessary for this unidirectional communication flow.

\section{Evaluation Design}
Describe the evaluation design, including the datasets used, metrics for evaluation, and the experimental setup.

\subsection{Datasets}
The evaluation framework relies on three custom-built datasets developed specifically for this thesis in collaboration with legal experts from the law firm BAHR AS. Each dataset is derived from a unique, real-world legal case processed through the Norwegian district court system. While the final verdicts and formal submissions from both parties were publicly available, the underlying case documents (e.g., correspondence, internal notes, and evidence) remained confidential. 

To facilitate a robust evaluation of the RAG (Retrieval-Augmented Generation) system, we have reconstructed these cases by generating synthetic document sets. These sets include simulated emails, technical reports, agreements, and contracts, all meticulously crafted to mirror the factual matrix and legal complexities described in the official court records. This approach ensures that the agent is tested against a realistic representation of a legal case file while maintaining necessary privacy standards.

The datasets are organized to simulate the chronological lifecycle of a legal proceeding. Each case is structured into several \textit{sessions}, each containing a sequence of \textit{queries}. This structure is designed to evaluate two critical capabilities of the agent:
\begin{enumerate}
    \item \textbf{Contextual Awareness}: The ability to maintain a coherent understanding of the case as it evolves through different stages of litigation.
    \item \textbf{Analytical Accuracy}: Each query is paired with a "gold standard" expected output, defined by legal experts. These references serve as the ground truth for measuring correctness, relevancy, and completeness.
\end{enumerate}

By following a chronological order, the sessions require the agent to handle increasing amounts of information and maintain consistency over time, reflecting the professional requirements of a legal practitioner managing an ongoing case.

\subsection{Metrics}
The evaluation will focus on several key metrics, measering both the quality of the agent's responses and its efficiency in terms of resource usage.
Metrics that are to be evaluated are:
\begin{itemize}
    \item \textbf{Correctness, Relevancy, and Completeness}: These semantic metrics are evaluated using the DeepEval framework. The agent's output is compared against a "gold standard" reference created in collaboration with legal experts. Each metric is scored on a scale from 0 to 1.
    \item \textbf{Self-consistency}: The degree to which the agent's output remains consistent across multiple queries and over time as the case evolves. \begin{equation}
    \text{Self-Consistency} = \frac{2}{n(n-1)} \sum_{i=1}^{n-1} \sum_{j=i+1}^{n} \text{cos}(\mathbf{e}_i, \mathbf{e}_j)
\end{equation}
\noindent where $n$ is the number of generated outputs, $\mathbf{e}_i$ and $\mathbf{e}_j$ are the sentence embeddings of the $i$-th and $j$-th output, and the cosine similarity is defined as:
\begin{equation}
    \text{cos}(\mathbf{e}_i, \mathbf{e}_j) = \frac{\mathbf{e}_i \cdot \mathbf{e}_j}{\|\mathbf{e}_i\| \|\mathbf{e}_j\|}
\end{equation}
    \item \textbf{BERTScore}: A metric that evaluates the similarity between the agent's output and a reference text using BERT embeddings \cite{zhang2020bertscoreevaluatingtextgeneration}.
    \item \textbf{Passrate}: The percentage of queries for which the agent's output meets a predefined quality threshold.
    \item \textbf{Efficiency Metrics}: \textbf{Token Usage} (total tokens consumed) and \textbf{Inference Time} (latency) are recorded to assess the practical viability of the system.
\end{itemize}
Correctness, relevancy, Completeness are all evaluated against the expected out (constructed in collaboration with legal experts) using DeepEval. 
The framework rates each response on a scale from 0 to 1, with a certain threshold for what is considered a "pass" for the passrate metric.

BERTScore is calculated based on the expected output. 
Self-consistency is evaluated by comparing the agent's responses across multiple queries and sessions to assess whether it maintains a coherent understanding of the case over time.
Token usage and inference time are recorded during the agent's operation.


\subsection{One-sided Hypothesis Tests}

\textbf{For quality/performance metrics} (correctness, relevancy, completeness, passrate, self-consistency, BERTScore):
\[
H_0: \mu_{\text{custom}} \leq \mu_{\text{baseline}} \qquad H_1: \mu_{\text{custom}} > \mu_{\text{baseline}}
\]
(and analogously vs. baseline+RAG)

\textbf{For cost/efficiency metrics} (token usage, inference time):
\[
H_0: \mu_{\text{custom}} \geq \mu_{\text{baseline}} \qquad H_1: \mu_{\text{custom}} < \mu_{\text{baseline}}
\]
(and analogously vs. baseline+RAG)

\textbf{Notation:}
\begin{itemize}
    \item $\mu_{\text{custom}}$ = population mean for the custom agent
    \item $\mu_{\text{baseline}}$ = population mean for the baseline agent
    \item $\mu_{\text{baseline+RAG}}$ = population mean for baseline with RAG
\end{itemize}
All tests are one-tailed / one-sided. \\ \\
